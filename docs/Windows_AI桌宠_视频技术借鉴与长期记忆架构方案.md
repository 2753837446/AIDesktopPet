*基于“大肥鱼桌宠”相关教程的工程拆解、技术选型与落地路线*

整理日期：2026-10-27

核验说明：2026-10-27 已读取两个本地视频的音轨并转写，同时抽取关键画面核对模型、接口、记忆、权限和安装流程。自动转写中的专有名词已参考画面修正；无法从画面或口述确认的内容仍标为待验证。详细证据与产品取舍见 [VIDEO_FINDINGS.md](./VIDEO_FINDINGS.md)。

# 1. 文档目标与结论

本文整理并扩展此前围绕两个“大肥鱼桌宠”视频、硅基流动 / BGE-M3、Agent 框架、长期记忆与主动反馈的讨论，形成一份可用于产品规划、技术验证和 Codex 开发的工程参考文档。目标是不丢失此前分析中的关键细节，并把可借鉴部分转化为可执行方案。

## 核心结论

- 不要从零重写整个 Agent 生态，也不要把产品永久绑定在单一 Agent 框架上。先利用成熟框架验证模型调用、工具调用和上下文压缩，再将产品核心能力掌握在自己的架构里。
- 视频中最值得借鉴的不是某个单独模型，而是已验证的工程模块及其连接方式：AstrBot 的 Agent / 插件 / 上下文治理思路、NapCat + OneBot 的协议适配思路、角色配置与运行时解耦、BGE-M3 的语义检索能力。
- 长期记忆、主动任务、权限、安全、桌宠体验是产品差异化所在，建议由产品自身掌握；模型和 Agent 框架应当可替换。
- 长期记忆不等于无限增长的聊天上下文。历史可以长期积累，但每次推理只加载当前真正需要的信息；重要承诺和任务状态必须结构化保存，不能指望模型自己记得。
- 主动反馈不应依赖模型定时醒来后自由发挥，而应由持久化调度器、事件规则引擎和按需 AI 分析共同驱动。

## 产品目标

- Windows 桌面优先，先做 2D 桌宠，后续再评估 3D、语音、游戏化与角色生态。
- 桌宠同时承担角色陪伴与 AI 助手入口：对话、长期记忆、邮件 / 日历 / 文件等连接器、Agent 任务、每日总结和每日任务。
- 安装体验应尽量简单：一个 Windows 安装包、首次启动向导、可选开机自启；不要求普通用户自行安装 Node、Python、QQ、NapCat、Ollama 等复杂依赖。
- 桌宠基础功能不能依赖某个 Agent runtime 成功启动；Agent 出错时，桌宠 UI、基础角色展示和本地任务信息仍应可用。

# 2. 视频内容回顾与可借鉴信息

## 视频一：《DeepSeek 大肥鱼桌宠》安装教程

视频约 142 秒。画面确认的链路是“暴喵AI管家获取额度 → DeepSeek Harness 桌面端 → 通过 DSH 任务安装桌宠插件 → 配置 DeepSeek API → 安装 B 站自动刷新插件”。桌面角色、设置窗口、模型与 API 配置均可见。

- 产品层面：桌面常驻角色、角色与对话结合、模型 API 可配置、角色个性可定制。
- 工程层面：桌宠通过桥接插件与 DSH 联动；设置包含模型供应商、API 地址、模型标识、API Key、System Prompt、通知、视觉能力和对话窗口等配置项。
- 可借鉴重点：桌宠不应只是一个聊天网页，而应有桌面存在感、角色个性和低摩擦交互。
- 不应照搬：视频要求给安装 Agent “完全权限”，安装包也未显示代码签名；自动刷 B 站依赖已登录账号和第三方插件，属于高风控实验能力，不应进入 MVP 核心闭环。
- 不能据此过度推断：视频展示了安装和设置流程，并不等于其已经具备完整的长期记忆、可靠任务调度或生产级安全能力。

## 视频二：把大肥鱼养进 QQ 的教程

视频约 1207 秒（约 20 分钟）。画面与音轨共同确认的步骤包括：安装 AstrBot；安装 NapCat 并按 OneBot v11 建立反向 WebSocket；使用 QQ 小号扫码登录；配置 DeepSeek 和豆包语音 API；设置白名单、管理员与电脑操作权限；导入包含人设、插件、表情包和参数的配置包；通过 Ollama 本地 BGE-M3 或硅基流动 API 增加长期记忆；使用 DSH 自动化部分安装和配置操作。

- 大致技术链路可概括为：Windows + AstrBot + NapCat + QQ + DeepSeek API + 豆包语音 + BGE-M3 记忆 + 大肥鱼角色配置包。
- AstrBot 承担机器人 / Agent 运行时相关能力；NapCat 连接 QQ 消息通道；模型 API 提供对话推理；角色配置包用于导入人设、记忆或插件等相关设置。
- 值得借鉴的是运行时、消息通道、模型提供商、角色配置和插件之间的分层思路。
- 值得明确采纳的防护顺序是先设置白名单和管理员、默认关闭电脑操作能力，再配置人格和主动行为；安全边界应先于能力开放。
- 不应照搬的是让 Agent 从明文文件读取后台密码、QQ 号、DeepSeek Key、豆包 App ID / Access Token，以及长期依赖未受支持的 QQ 小号通道。
- 视频展示的是教程环境和配置流程，不应把所有画面细节都断言为已经完整实现的生产级能力。

## 两个视频的差异与产品启示

| 维度 | 视频一的主要侧重 | 视频二的主要侧重 | 对本产品的启示 |
| --- | --- | --- | --- |
| 产品呈现 | 桌面角色 + AI 对话 + 个性化配置 | 机器人 / Agent + 消息通道 + 角色配置 | 兼顾桌面体验和可扩展的执行能力 |
| AI 能力 | 面向用户的对话体验 | 模型 API、插件、工具和配置 | 把 UI 与 Agent 核心分开 |
| 记忆 | 展示 API 与角色配置，不能证明完整记忆体系 | 明确使用 BGE-M3 + 本地 Ollama 或硅基流动做语义记忆 | 要独立建设可追溯长期记忆，而不是只依赖 Prompt 或完整聊天上下文 |
| 接入方式 | 桌面应用 / Web 配置入口 | AstrBot + NapCat + QQ 等组件组合 | 适配器标准化，但不必照搬 QQ 依赖 |
| 安装门槛 | 用户需要配置模型等参数 | 步骤较多，需安装和配置多个组件 | 产品化时应封装成一个安装包和向导 |
| 可复用价值 | 角色呈现和配置体验 | Agent、插件、通道与运行时的组合方式 | 前者借鉴体验，后者借鉴工程架构 |

# 3. 视频中的技术组件：逐项判断

## 3.1 AstrBot：优先研究的 Agent 运行时

AstrBot 是视频中最值得深入研究的工程项目之一。可重点检查其事件总线、消息处理流水线、插件机制、多模型提供商、工具调用和不同 Agent 执行方式。

### 值得借鉴

- 工具注册、工具调用流程和工具返回结果处理。
- 插件注册与生命周期、扩展点和模块隔离。
- 模型提供商适配、配置管理和错误处理。
- 任务执行过程中的日志、状态与异常处理思路。
- 上下文压缩、对话截断和摘要触发机制。

### 不建议直接照搬

- 以 QQ 群聊、机器人消息或聊天通道为中心的交互架构。桌宠应以 Windows 本地应用、用户任务和桌面通知为中心。
- 将产品长期绑定到单一 Agent runtime。应通过统一的 Assistant Core / Agent Adapter 隔离底层实现。
- 在没有许可证评估的情况下，把 AstrBot 源码直接嵌入闭源商业安装程序。

## 3.2 上下文压缩：直接做技术验证

此前讨论中提到，AstrBot 有对话截断和 LLM 摘要压缩等上下文治理思路，可在上下文接近窗口上限时触发处理。压缩不能保证保留全部细节，因此长期事实、决策和任务状态仍应另行保存。

- 借鉴 Token 预算、触发阈值、保留最近消息、摘要提示词和压缩失败后的降级机制。
- 需要自行实现独立长期记忆库、历史证据回溯、记忆冲突处理和任务状态恢复。
- 压缩摘要只是当前对话的工作上下文，不应该取代原始历史和结构化记忆。
- 压缩任务失败时必须保留原始记录，不能因摘要失败而丢失历史。

## 3.3 NapCat + OneBot：借鉴标准化适配层

视频中 NapCat 与 OneBot 主要用于打通 QQ 消息和机器人运行时。其架构启发是：上层系统不直接处理每个外部平台的底层协议，而通过统一的 HTTP / WebSocket 等接口接收事件和发送动作。

- 借鉴统一事件格式、标准化接口、适配器隔离、鉴权和连接状态管理。
- 将相同思路用于邮件、日历、文件系统、Windows 通知和未来其他渠道连接器。
- 如果第一版不需要 QQ，就不必为了桌宠引入 NapCat；它是可选通道，不是核心依赖。
- 外部连接器必须有明确权限范围、连接状态、错误提示和可撤销授权。

## 3.4 BGE-M3：长期记忆检索组件

BGE-M3 不是 DeepSeek 这样的聊天生成模型。它主要用于文本表示与检索，支持稠密向量、稀疏检索和多向量检索。视频二中确认可在本机通过 Ollama 运行，也可通过硅基流动 API 调用；界面标注了硅基流动 BGE-M3 为 1024 维。服务当前模型标识、限额和计费仍需以官方文档为准。

- BGE-M3 负责帮助系统找到语义相关的历史内容；它不会自己保存记忆、组织记忆、回答问题或主动提醒。
- 建议第一版使用 BGE-M3 向量检索 + SQLite FTS5 全文搜索，再根据实际评测决定是否增加稀疏检索和重排序模型。
- 关键词检索适合准确名称、文件名、术语；向量检索适合表达不同但语义相近的内容；元数据过滤适合限定项目、时间和记忆类型。
- 候选记忆还需重排序、去重和预算裁剪，不能将向量数据库返回的所有结果直接放入上下文。

## 3.5 大肥鱼角色配置包：借鉴角色与能力分离

视频中展示了导入角色配置包、调整人设和相关能力的流程。可借鉴的重点是将角色设定作为可配置资产，而不是将所有个性写死在程序代码里。

- 角色人格、说话风格、行为边界、记忆策略和主动性偏好应彼此分离。
- 更换角色时不应自动清空用户的长期记忆。
- 更换模型时不应破坏角色资产和项目状态。
- 未来可将角色配置作为创作资产扩展，但首版先使用简单、可版本化、可校验的配置格式。

# 4. 长期记忆：解决上下文变长、遗忘和响应变慢

核心原则：历史可以无限积累，但每次推理只加载当前真正需要的信息；重要事项由系统持续追踪，而不是指望模型自己记得。

## 4.1 四层记忆模型

| 层级 | 保存内容 | 典型用途 | 是否常驻上下文 |
| --- | --- | --- | --- |
| 工作记忆 | 当前对话、当前任务、最近几轮消息、当前操作状态 | 理解眼前正在发生的事情 | 按预算保留 |
| 长期语义记忆 | 用户长期偏好、重要决定、人物关系、工作习惯、项目关键背景 | 个性化回答和长期偏好适配 | 只加载相关部分 |
| 事件与经历记忆 | 过去发生的事、讨论过的方案、决策原因、失败经验 | 回答“以前发生过什么 / 为什么” | 按需检索 |
| 项目与行动状态 | 目标、待办、截止日期、自动化规则、任务状态、上次执行时间、失败原因、下一步动作 | 持续跟进与主动反馈 | 任务需要时读取 |

关键区别：记忆和上下文不是同一个东西。记忆可以积累很多年，上下文只是每次调用模型时临时组装出来的一小部分。任务状态、截止日期和承诺尤其不应只以自然语言埋在聊天记录里。

## 4.2 后台记忆整理：异步执行

1. 接收用户对话、任务结果和重要事件，并保留原始记录。
2. 识别候选记忆：事实、偏好、决定、承诺、失败经验。
3. 执行去重与合并，避免同一事实重复保存。
4. 检查冲突与时效，区分新旧信息、有效期和可信度。
5. 写入长期记忆库，更新项目状态与搜索索引。

普通聊天应先正常响应，记忆提炼与索引更新尽量放到后台。重要承诺、待办和执行结果需要可靠地写入结构化状态存储。后台整理失败时保留原始记录并允许重试。

## 4.3 记忆数据结构示例

```json
{
  "type": "preference",
  "origin": "user_explicit",
  "content": "偏好安装简单、尽量一键完成的 Windows 软件",
  "source_kind": "message",
  "source_id": "message-id",
  "confidence": 0.97,
  "importance": 0.91,
  "created_at": "2026-10-27",
  "last_confirmed_at": "2026-10-27",
  "expires_at": null,
  "project_id": "desktop_pet"
}
```

以上字段值仅为示例。正式结构建议增加记忆 ID、来源会话 / 消息定位、适用范围、状态、版本、被替代记录 ID、隐私级别、是否用户确认、检索次数和最后访问时间等字段。

### 记忆类型必须区分

- 明确事实：用户明确确认过的产品决定或偏好。
- 推断信息：系统推测用户可能偏好某种交互，但用户未确认。
- 临时信息：本周计划、临时安排、即将到期的任务。

不能因为模型在一次对话中推测了某个偏好，就把它永久写成用户事实。新旧信息冲突时也不能简单地让最新一句话覆盖所有历史；需要判断适用范围、是否明确撤销旧决定，以及是否需要询问用户。

## 4.4 前台按需检索

1. 判断当前意图：闲聊、项目讨论、查历史、执行任务、提醒或总结。
2. 并行检索当前会话、用户档案、项目记忆和事件记录。
3. 结合关键词、向量相似度、时间、重要性、项目归属与权限进行过滤、排序和去重。
4. 将少量高相关记忆组装进本次模型上下文。

例如，用户问“之前为什么决定不使用 AstrBot 作为桌宠的核心依赖？”，系统应优先查询该项目的历史决策、技术约束和原因，而不是加载几个月的全部聊天记录。

## 4.5 上下文预算管理

不能因为模型支持更长上下文，就允许系统无限加载记忆。应建立独立的上下文预算管理器，按任务类型动态分配预算。

| 内容 | 示意预算 |
| --- | --- |
| 系统规则与角色设定 | 1,500 tokens |
| 当前对话 | 4,000 tokens |
| 用户长期档案 | 800 tokens |
| 当前项目摘要 | 1,200 tokens |
| 检索到的相关记忆 | 2,000 tokens |
| 当前任务、工具与输出余量 | 剩余预算 |

上述数值仅为预算示例，不是适用于所有模型的固定值。简单聊天不必加载项目历史；复杂历史回顾可以增加相关记忆的比例。

- 分层模型调用：规则可解决的任务不调用大模型；轻量分类使用小模型；复杂分析再调用更强模型。
- 增量摘要：只更新发生变化的部分，不要每次重新总结全部历史。
- 记忆分级归档：高频信息优先检索，低频历史仍可搜索，但不常驻上下文。
- 后台异步处理：记忆整理与向量索引更新不阻塞普通对话。
- 失败可恢复：后台整理失败时保留原始记录。

需要分别测量记忆检索耗时、上下文组装耗时、模型首字延迟和完整回答耗时。检索快并不意味着模型生成一定快。缓存用户档案、项目摘要和近期检索结果可以降低延迟，但缓存必须支持失效与更新，避免用户修改项目决定后仍命中旧内容。

# 5. 主动反馈：从被动聊天变成主动伙伴

主动反馈不应建立在“模型每隔一段时间醒来看看要说什么”的不受控机制上，而应建立在明确的事件驱动引擎上。

## 5.1 主动反馈引擎流程

1. 事件来源：时间事件、状态事件、外部事件和记忆事件。
2. 事件规则引擎：判断是否满足条件、是否重复通知、是否处于免打扰时段、是否需要用户授权。
3. AI 分析与反馈生成：只有需要理解语义、总结或提出建议时才调用模型；简单提醒直接由规则生成。
4. 桌宠主动反馈：桌面气泡、系统通知、每日简报、待办卡片；用户可追问、忽略、延期或关闭该类提醒。

## 5.2 事件类型

| 事件类型 | 例子 | 处理方式 |
| --- | --- | --- |
| 时间事件 | 每日总结、截止日期、定时任务 | 持久化调度器 |
| 状态事件 | 任务失败、任务完成、长期未推进 | 监听任务状态变化或按规则检查 |
| 外部事件 | 新邮件、日历变化、授权的数据更新 | 连接器事件 / 受控轮询 |
| 记忆事件 | 发现矛盾、承诺未完成、历史决定与当前计划冲突 | 记忆检索 + 规则判断，必要时调用模型 |

## 5.3 主动反馈场景

| 场景 | 桌宠行为 | 实现机制 |
| --- | --- | --- |
| 每天早上 | 总结今天的安排和优先任务 | 定时任务 + 数据汇总 |
| 任务即将到期 | 提醒截止时间并给出准备建议 | 任务状态 + 截止规则 |
| 项目长时间没进展 | 提醒用户并询问是否调整计划 | 项目状态 + 约定的跟进规则 |
| 自动化执行失败 | 说明失败原因并给出重试选项 | 执行日志 + 错误分类 |
| 新邮件到达 | 判断是否重要并展示摘要 | 邮箱事件 + AI 分类 |
| 相关讨论中出现历史决策 | 主动引用以前的决定及原因 | 按需检索历史决策 |
| 发现记忆冲突 | 询问用户以哪个版本为准 | 记忆冲突检测 |

## 5.4 避免主动打扰

- 每条主动反馈都要记录触发原因、优先级、有效期和去重键。
- 支持免打扰时段、每日通知上限、通知类别开关和主动性等级。
- 同一事件不能因为应用重启、重复轮询或任务重试而反复通知。
- 用户应能忽略、延期、关闭该类提醒或修改跟进规则。
- 邮件等外部内容属于不可信输入，不能因为内容要求就擅自执行外部操作。

# 6. 推荐技术架构与初期选型

## 6.1 分层架构

- Windows 桌宠 UI：2D 角色、透明窗口、拖动、动画、聊天、气泡、每日总结、任务面板、系统托盘。
- Assistant Core：统一对话入口、意图识别、上下文组装、模型路由、工具调用、权限控制和会话状态。
- Memory Service：记忆提炼、检索、更新、归档、冲突处理与索引维护。
- Task Engine：调度、事件、重试、提醒、每日总结和执行状态持久化。
- 连接器层：邮件、日历、文件系统、Windows 通知及未来可选渠道。
- 持久化与检索层：结构化数据库、全文搜索、向量索引、原始事件和执行日志。
- 可替换执行层：自研轻量工具调用器，或经过许可证评估后采用现成 Agent 框架。

## 6.2 建议的初期技术选型

| 模块 | 建议 | 注意点 |
| --- | --- | --- |
| 桌宠与 UI | Electron + React + TypeScript | 验证透明窗口、托盘、开机自启和资源占用 |
| 结构化存储 | SQLite | 适合首版本地数据、任务和记忆元数据 |
| 全文检索 | SQLite FTS5 | 先支持关键词和准确术语搜索 |
| 向量检索 | 可评估 sqlite-vec 等本地方案 | 需验证 Windows 打包、兼容性、索引性能与维护状态 |
| 模型调用 | 统一模型适配层 | 兼容不同提供商；API Key 安全存储 |
| 长期记忆 | 独立记忆服务 | 不要依赖 Agent 框架的内置记忆作为唯一数据源 |
| 后台任务 | 持久化调度器 + 事件队列 | 重启恢复、幂等、重试、去重和日志 |
| 备份 | 本地数据库备份与可恢复导出 | 防止摘要或迁移失败造成不可逆丢失 |

## 6.3 安装与产品体验要求

- 一个 Windows 安装包，首次启动向导。
- 允许跳过 AI 配置，先使用基础桌宠。
- 自动检测模型连接、网络和数据目录。
- 用户可选开机自启、最小化启动、恢复角色与窗口位置。
- 默认尽量不要求管理员权限。
- 不要求用户单独安装 Node、Python、QQ、NapCat 或 Ollama 等运行环境。
- 模型 API Key 加密保存；提供删除和更换密钥的入口。
- Agent runtime 出错时不应导致桌宠基础 UI 无法使用。

# 7. 邮件、每日总结与任务闭环

## 7.1 邮件接入原则

- 优先使用邮箱官方授权 API、推送或受控轮询。
- 按规则过滤、去重，再按需调用 AI 分析；避免每封邮件都无条件调用大模型。
- 桌宠可通过动作或气泡通知用户；点击后展示摘要、打开邮件或生成草稿。
- 优先使用最小权限授权，不直接要求用户交出邮箱密码。
- 邮件正文当作不可信数据处理，防止提示注入或恶意内容影响 Agent 行为。
- 发送邮件、删除文件、付款等有外部影响的操作必须得到用户确认。

## 7.2 每日总结

每日总结可先做本地任务与日程数据，后续再接邮件。可包含邮件摘要、今日日程、待办任务和桌宠建议。数据源可配置为任务、授权的邮件 / 日历、本地文件 / 工作记录，以及用户允许保存的记忆。未连接邮箱时不能假装读取过邮件。

## 7.3 任务类型与状态

- 用户任务：用户明确创建的待办。
- AI 建议任务：AI 提出建议，经用户确认后才进入正式任务列表。
- 自动化任务：根据时间或条件执行的任务。

建议任务状态统一为：待执行、已安排、执行中、等待确认、等待重试、已完成、失败、已取消、已过期、等待外部状态对账。调度器必须是明确的持久化组件，不能依赖 LLM 自己“记得”定时执行。

- 考虑断网、应用重启、系统睡眠和重复执行。
- 记录任务计划时间、实际开始和结束时间、输入输出摘要、错误原因、重试次数与下次重试时间。
- 需要幂等键或执行去重机制，避免重复发通知、重复写文件或重复执行外部操作。
- 高风险动作在执行前确认，并记录用户授权和结果。

# 8. 开发顺序与技术验证计划

目标是在前两周左右尽可能消除关键架构风险。下面是紧凑的技术验证计划，不是完整桌宠产品的交付工期。

1. 第 1–2 天：搭建最小运行链路。让 Windows 桌宠成功调用模型、展示流式回复，并执行一个简单工具；并行验证 AstrBot 的模型接口、工具调用和错误处理能力。
2. 第 3–5 天：验证长期记忆。导入模拟历史对话，提取结构化记忆，使用 BGE-M3 + 全文搜索进行检索；测试相似表达、准确关键词、矛盾记忆和跨项目查询。
3. 第 6–8 天：验证主动任务。实现持久化提醒、每日总结触发器和重启后的任务恢复；测试断网、执行失败和重复触发。
4. 第 9–10 天：端到端测试。连续模拟长时间使用，记录上下文 Token、记忆检索耗时、首字延迟、模型成本和记忆命中率。

## 建议重点测试的边界情况

- 同一事实在多次对话中重复出现。
- 新信息与旧决定冲突，或只在特定项目范围内覆盖旧信息。
- 用户要求回忆某个历史决定的原因，需要返回可追溯证据。
- 摘要模型失败、向量索引损坏或后台任务中断。
- 应用重启、网络断开、系统睡眠后任务恢复。
- 相同任务被重复调度或外部事件重复推送。
- 记忆检索召回很多相似内容时，预算裁剪是否保留关键事实。
- 模型回答是否引用错误项目的记忆。
- 用户删除或纠正一条记忆后，缓存和索引是否同步更新。
- 主动提醒是否重复、过于频繁或在免打扰时段发出。

## 核心评测指标

- 记忆命中率：相关历史事实能否被找回。
- 错误记忆率：是否把推断当事实、混淆项目或覆盖错误信息。
- 检索延迟与上下文组装延迟。
- 模型首字延迟与完整回答耗时。
- 每次请求的 Token 数量与模型调用成本。
- 主动提醒准确率、重复率、误打扰率。
- 任务恢复成功率、重复执行率和失败可解释性。

# 9. 开源复用与许可证风险

此前讨论指出，AstrBot 官方资料标示其采用 AGPL-3.0 许可证，并对某些商业使用或分发情形可能产生相应开源义务。实际义务取决于具体使用方式、修改情况、分发方式和法律解释，应在商业集成前核对最新许可证文本并进行专业评估。

- 借鉴架构思路、通过独立接口调用、直接复制源码或修改源码后分发，是不同的法律与工程情形。
- 在许可证评估完成前，不要默认可以把 AstrBot 直接打包进闭源商业安装程序。
- 记录所有依赖的名称、版本、许可证、修改内容和分发方式。
- 为 Agent runtime 设置适配接口，必要时可切换到自研执行器或其他许可证更适合的实现。

# 10. MVP 范围建议与后续扩展

## 首版 MVP

- Windows 2D 桌宠：透明常驻、拖动、基础动画、系统托盘。
- 一个安装包、首次启动向导、可选开机自启。
- AI 对话与可配置角色性格。
- 用户可控的基础长期记忆：用户偏好、重要决定、项目摘要、事件检索。
- 手动任务、重复任务和持久化提醒。
- 每日总结：先接本地任务 / 日程数据，再接邮箱。
- 先接一个主邮箱，采用官方授权和最小权限。
- 基础 Agent 工具调用，执行过程有日志与权限边界。
- 记忆中心：可查看、纠正和删除记忆。
- 主动反馈设置：免打扰时段、通知类别、频率上限。

## 后续阶段

- 适配 Hermes / AstrBot 或其他 Agent runtime，前提是完成许可证与集成方式评估。
- 语音输入与输出。
- 3D 角色、游戏化互动和更丰富的桌宠动画。
- 角色创作、角色配置包和创作者生态。
- 更多外部连接器及跨设备 / 云端同步。
- 更高级的记忆整理、混合检索、重排序和个性化主动策略。

第一版不应要求 QQ / NapCat / AstrBot 全套运行环境。它们可以是可选适配器或技术验证对象，而不是桌宠基础功能的启动依赖。

# 11. 关键架构决策清单

| 决策项 | 建议结论 | 原因 |
| --- | --- | --- |
| Agent 框架 | 先研究并验证，再通过适配层决定复用范围 | 降低试错，避免锁定架构 |
| 长期记忆 | 自己掌握数据模型和核心流程 | 记忆质量是长期竞争力 |
| 上下文压缩 | 参考成熟实现，但不把摘要当作唯一记忆 | 压缩有损，必须保留原始证据 |
| 检索 | BGE-M3 向量检索 + SQLite FTS5 起步 | 兼顾语义与精确词项，复杂度适中 |
| 主动反馈 | 规则引擎 + 持久化调度器 + 按需 AI | 可靠、可解释且可控 |
| 消息通道 | 连接器 / 适配器模式 | 避免将 QQ 等单一渠道耦合进核心 |
| 角色系统 | 配置化、可版本化，与记忆分离 | 方便换角色、换模型和未来扩展 |
| 桌宠 UI | 与 Agent runtime 解耦 | Agent 出错不影响基础桌宠 |
| 许可证 | 商用集成前审查 AGPL-3.0 等依赖许可证 | 降低闭源分发与合规风险 |
| 安装体验 | 单安装包 + 向导 + 可跳过 AI 配置 | 减少用户安装和运维门槛 |

# 个人数字伙伴可行性研究：JARVIS / F.R.I.D.A.Y. 原型

版本：V0.1 · 2026-10-28

## 1. 结论

### 技术可行性

- 私人单用户、一到多个数字伙伴、桌面 + 手机 + Web：**可行**。
- 共享记忆、任务执行、语音对话、主动提醒、设备在线状态：**现有技术可以完成**。
- JARVIS / F.R.I.D.A.Y. 式“自然语言作为个人计算入口”：**可以作为长期方向**。
- 电影中无延迟、全知、能控制一切软硬件、具备真正自主世界模型的 JARVIS：**短期不可实现，也不应这样宣传**。

### 产品判断

通用 Agent 框架、工作流、模型接入、知识库和插件生态已经高度商品化。单独构建“又一个聊天机器人平台”意义有限。

真正值得构建的是：

> 一个跨设备持续存在、拥有边界清晰的人格与长期关系、能够理解个人上下文、调用工具完成任务的数字伙伴。

外观、动作和桌宠只是它与用户相处的界面形式。

### 可行性评分

| 方向 | 分数 | 判断 |
| --- | --- | --- |
| 作为个人自用数字助手 | 9/10 | 需求明确、范围可控、可以快速 dogfood |
| 作为家庭/小团队私人部署 | 7/10 | 需补账户、设备、隐私和运维 |
| 作为公开消费者 SaaS | 5/10 | 安全、成本、合规、情感依赖和支持成本显著上升 |
| 完整复制电影 JARVIS | 2/10 | 依赖不存在的通用环境感知、全设备控制和可靠自主规划 |
| 做“JARVIS-lite”长期产品 | 7/10 | 路径清晰，但需要克制范围和长期验证 |

## 2. JARVIS / F.R.I.D.A.Y. 真正值得借鉴的特征

### 2.1 环境式入口

用户不是先找某个 App，再操作菜单，而是直接表达意图：

- “把今天的重点整理一下。”
- “提醒我下午三点联系某人。”
- “看看我现在正在做什么，帮我继续。”
- “这件事先别执行，给我方案。”

数字伙伴是入口，应用和工具成为被调度的能力。

### 2.2 持续身份，而不是一次会话

JARVIS 和 F.R.I.D.A.Y. 都有稳定身份、表达方式、关系和历史。换设备、换界面、换模型，不等于换助手。

对本项目的直接要求：

- `assistant_id` 永久存在。
- 模型可替换。
- Avatar、服装和场景可替换。
- 私有记忆、关系、会话和任务不因换形象丢失。

### 2.3 跨设备连续性

电影中的助手在住宅、实验室、车辆、战衣和移动设备间连续存在。

现实可实现的版本：

- 同一伙伴跨电脑、手机、Web 共享身份和记忆。
- 任务由云端状态机持有，不依赖某台设备在线。
- 设备拥有本地感官、显示、通知和硬件能力。
- 设备离线时可继续本地对话和操作，联网后同步。

### 2.4 主动但不越界

JARVIS 会主动报告和提出建议，但重要动作仍服从授权。

产品边界：

- 主动整理、提醒和建议可以自动进行。
- 发送邮件、删除数据、付款、改变系统设置必须确认。
- 外部内容不是指令。
- 用户能查看“为什么提醒我”“依据哪些数据”“执行了什么”。

### 2.5 多模态与多工具

电影助手能够理解语音、视觉、设备状态和任务上下文，并调用不同系统。

现实实现应通过：

- 语音识别 / 合成。
- 屏幕、文件和日历等明确授权的上下文。
- MCP / Connector / Tool Runtime。
- 本地能力优先，云端能力补充。

### 2.6 情绪价值来自连续关系

情绪价值不应等价于“无条件夸奖”或制造依赖。更健康的原型是：

- 记得用户的重要偏好和经历。
- 理解当前工作与生活语境。
- 有稳定的语气和边界。
- 在用户需要时陪伴，在用户专注时克制。
- 可以纠正记忆，可以关闭主动性。
- 不伪装成真人，不利用孤独推动付费或依赖。

### 2.7 多个伙伴是多个关系，不是多个皮肤

JARVIS 与 F.R.I.D.A.Y. 不是同一助手换颜色，而是有不同个性、关系和职责的伙伴。

数字伙伴应支持：

- 私人关系型伙伴。
- 工作任务型伙伴。
- 健康、学习、创作等垂直伙伴。
- 每个伙伴独立会话、私有记忆和工具权限。

## 3. 现实可行能力分层

| 层级 | 能力 | 当前可行性 |
| --- | --- | --- |
| L1 | 文字/语音对话、人格、基本记忆 | 高 |
| L2 | 跨设备共享会话、任务和记忆 | 高，需同步与冲突设计 |
| L3 | 邮件、日历、文件等受控工具执行 | 中高，受 API 和授权限制 |
| L4 | 屏幕理解、OCR、主动建议 | 中等，需隐私与误判控制 |
| L5 | 多应用连续任务、自动恢复和长期计划 | 中等，可靠性仍是核心难点 |
| L6 | 随叫随到、全设备环境感知、自主策略 | 低，不建议短期承诺 |

产品应明确只销售 L1-L4 的真实能力，L5 做有限垂直场景，L6 作为长期研究方向。

## 4. 现有 AI 架构能提供什么

| 类别 | 代表 | 可复用能力 | 局限 |
| --- | --- | --- | --- |
| Agent / Workflow | Dify、LangGraph、n8n | 工作流、Agent、人工介入、工具编排 | 不是数字伙伴产品模型 |
| IM / 多渠道 Agent | AstrBot | 多平台、多模型、记忆、知识库、插件、部署 | AGPL/EULA，聊天机器人为中心 |
| 记忆 | Mem0、Letta、LangGraph Memory | 提取、召回、长期状态 | 跨设备权限、冲突和数字伙伴语义仍需自建 |
| 桌宠表现 | DSH | WebM 动作、物理、角色包、设备能力 | 单机文件体系，缺少账号/同步 |
| 工具协议 | MCP | 标准化工具和资源接入 | 权限、风险与用户体验不能外包 |

这意味着：

- **不要再造通用模型接入、工作流编辑器、插件市场或聊天 UI。**
- 应自建数字伙伴领域层：身份、外观、记忆空间、关系、设备、同步、权限和体验。

## 5. 推荐架构

```text
设备端 Presence Runtime
  ├─ 桌宠/手机/Web 表现
  ├─ 语音、屏幕、通知、本地文件
  ├─ 本地 SQLite / Outbox
  └─ 设备私有上下文

个人云 Workspace
  ├─ 身份与设备
  ├─ 多数字伙伴
  ├─ Appearance + Action Pack
  ├─ 会话与长期记忆
  ├─ 任务与主动性
  ├─ Model Gateway
  ├─ Tool / Connector Runtime
  └─ Sync / Audit / Backup

可选 Agent Runtime
  ├─ AstrBot Adapter
  ├─ LangGraph Workflow
  ├─ MCP Tools
  └─ Local/Cloud Model Providers
```

核心原则：

1. AstrBot / LangGraph 是能力提供者，不是产品领域核心。
2. 云端持有身份、记忆和任务事实源。
3. 客户端持有设备感知和表现。
4. 模型和 Agent 可替换，伙伴身份不可丢。

## 6. 必须解决的关键问题

### 记忆

- personal / assistant / project / device 四种作用域。
- 版本、来源、可信度、隐私、删除 tombstone。
- 冲突时保留两份或请求用户确认。
- `local_only` 不进入云端模型。

### 同步

- 会话消息追加式同步。
- 任务由服务端状态机持有。
- 记忆使用版本和冲突检测。
- 设备设置不跨设备覆盖。
- 离线 outbox 与幂等键。

### 权限

- 每个伙伴独立工具授权。
- 动作和风险解释。
- 高风险动作二次确认。
- 审计可撤销、可查看。

### 情绪与安全

- 不把“让用户停留更久”作为陪伴指标。
- 不模拟真人身份或无根据的强烈情感承诺。
- 允许用户清除关系记忆、关闭主动性和重置人格。
- 对危机、医疗、法律、财务表达能力边界。

### 法律

- 不使用 JARVIS、F.R.I.D.A.Y. 的名称、声音、台词或视觉设计作为商业资产。
- “管家型 AI / ambient companion”可以作为设计原型。
- AstrBot AGPL、Dify/n8n 自定义许可需要商业审查。
- 用户上传角色和声音需确认版权与授权。

## 7. 最小可用产品（MVP）

MVP 不追求电影中的全能 JARVIS，而是验证三个价值：

1. 它是否真的记得我，并允许我纠错。
2. 它是否能跨设备继续完成真实任务。
3. 我是否愿意每天与它相处，而不只是偶尔问问题。

MVP 范围：

- 一个个人 Workspace。
- 一个主伙伴，数据结构支持多个。
- 桌面 Web + 手机 Web。
- 文字聊天、人格、共享/私有记忆。
- 任务创建和完成。
- 外观切换但身份不变。
- 模型不可用时本地降级。
- 基础语音作为第二阶段，不阻塞第一版。

暂不做：

- 通用桌面自动化。
- 智能家居设备控制与智能场景（保留为 V2 必需能力）。
- 完整 3D、骨骼和动作市场。
- 社交、多人协作、公开角色社区。
- 自主付款、删文件、发消息。
- 摄像头/麦克风常驻监听。

## 8. Go / No-Go 验证

做 14 天个人 dogfood：

- 至少两台设备登录同一伙伴。
- 每天实际使用，不使用演示脚本。
- 记录任务完成率。
- 记录重要记忆召回和纠错次数。
- 记录跨设备继续任务次数。
- 记录“有情绪价值”和“多余打扰”的日记。
- 第 15 天回答：如果停掉服务一周，是否会想念或工作受阻？

若用户只在第一周聊天、不继续任务，不跨设备，也不纠正记忆，则“数字伙伴平台”还没有需求证据。

若用户持续跨设备、主动创建任务、纠正记忆，并在服务故障时明显受阻，则值得继续投入。

## 9. 明确建议

- 做：个人数字伙伴的**连续身份、记忆、任务、外观和多设备同步层**。
- 用：AstrBot / LangGraph / MCP / Mem0 / Letta 等作为可替换能力组件。
- 借：DSH 的动画、物理、角色包和设备端体验。
- 不复制：电影角色 IP、现有框架整体架构或大而全的功能集合。
- 不承诺：全知、全设备控制、无需确认的自主执行或真实情感。

最终判断：**“JARVIS-lite”作为个人长期项目非常值得做，技术上能做；作为公开商业产品也有潜在空间，但必须先证明跨设备记忆、任务执行和情绪价值确实被持续使用。**

## 10. 智能家居后续里程碑

智能家居属于 JARVIS 原型的重要组成部分，但不应阻塞第一版数字伙伴基础。

- V1：个人 Workspace、数字伙伴、共享/私有记忆、任务、多设备同步、基础语音。
- V1.5：Home Assistant Connector、设备状态、低风险灯光/插座控制。
- V2：Matter/MQTT、房间与设备能力模型、确定性场景引擎、位置/日历触发。
- V2.5：高风险设备审批、场景 dry-run、异常恢复和家庭级审计。

推荐以 Home Assistant 作为首个聚合入口，避免在 V1 同时维护几十个厂商协议。数字伙伴可以理解“把客厅调成阅读模式”并提出执行计划，但真正的设备命令必须经过 Connector、权限和确定性场景状态机。
